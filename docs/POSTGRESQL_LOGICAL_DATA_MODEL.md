### 1.3 Preserved non-negotiable constraints

- CARES backend: **Python**. Primary relational database: **PostgreSQL**. Initial architecture: **modular monolith**.
- MELIRA: **external AI SaaS providers only**; no local LLM inference, local AI compute, or local GPU infrastructure. CARES core must work without MELIRA.
- Multi-tenant isolation enforced at application and database boundaries. Tenant authority from trusted verified context, not client-supplied tenant IDs or user-settable PostgreSQL GUC values. PostgreSQL RLS is defense in depth, not replacement for application authorization.
- Separate logical database roles: `cares_api_runtime`, `cares_ingest_runtime`, `cares_worker_runtime`, `cares_migration`, `cares_maintenance`. No ordinary runtime role treated as database owner, SUPERUSER, or BYPASSRLS.
- **Asset licensing invariants:** exactly one licensed asset = one unique monitored device within a tenant; multiple data sources for same device must not be counted more than once; data source is not a billable asset; all device types equal licensing weight; licensing separate from technical resource quotas; IP/hostname are observations not stable canonical identity; ambiguous identity must not auto-merge; canonical asset identifiers stable and non-reusable; identity/licensing/lifecycle/history changes must support atomicity and durable idempotency.
- **Source-device identity model:** preserve conceptual distinction between `asset`, `data_source`, `asset_data_source`, `source_device_key_id` (or stable source-device key), `source_device_fingerprint_alias`, and identity-claim/observation records (`asset_identity_alias` / equivalent). No two competing sources of truth for a source-device binding. Cardinality/ownership between `asset_data_source` and `source_device_key_id` explicitly analyzed. Fingerprint aliases are versioned lookup identities, not permanent binding identities; multiple valid aliases may temporarily point to same stable binding during approved key-rotation overlap. Never use raw source identifiers as database uniqueness keys.
- ADR statuses preserved (ADR 0006 remains **Proposed**).

## 2. Classification conventions and analysis method

- **Decision status (used consistently):** `Required` (explicitly established requirement/invariant), `Proposed` (technically recommended, not yet accepted), `Assumption` (temporary for understandability), `Open Decision` (cannot be finalized without further technical/security/product/commercial/legal/privacy/owner approval). Proposed/Assumption/Open Decision are not promoted to Required.
- **Entity attributes are logical-level:** names and purposes are indicative for understanding; they are not physical column definitions, SQL types, or constraints.
- **Tenant-inclusive FK enforcement:** where a tenant-owned entity relates to another tenant-owned entity, the physical schema is expected to require tenant-inclusive foreign-key/constraint enforcement so cross-tenant references are structurally prevented (physical design deferred).
- **RLS applicability:** stated as expected future applicability/category; no RLS SQL policies are designed here.

**Identity model notes (critical distinctions):** (1) **Agent identity** (runtime/installation principal) is distinct from (2) **agent enrollment credential** (secret/token/cert material reference/issuance state) and from (3) **connector/data-source identity** (`data_source`), which is distinct from (4) **source-device identity** (stable source-device binding represented by authoritative `asset_data_source` owning immutable `source_device_key_id`, plus versioned fingerprint aliases and claims/provenance for that reported device context) and from (5) **canonical CARES asset identity** (`asset`). These must not be collapsed into one table or identifier. **Round 1.1 recommendation (Proposed, not approved):** `asset_data_source` is the single source of truth for stable binding identity/lifecycle; a separately materialized `source_device_key` entity, if any, must be 1:1 dependent/non-authoritative with no competing attributes. Agent enrollment/credential records are modeled minimally as proposed integration/security references where needed; detailed agent protocol schema is out of Round 1 scope.

| Tenant-scoped operational data | `asset`, `data_source`, `asset_data_source` (authoritative stable binding identity), dependent `source_device_key` projection (if any), `source_device_fingerprint_alias`, `asset_identity_claim`, `identity_resolution_case`, lifecycle/merge/split/typed lineage, license/subscription/usage/reservation/ledger/event records, `event_receipt` (namespace-aware), `security_event`, `outbox_message`/attempts, `alert`, `incident_case`, vulnerability findings, inventory observations, integration config | Owned by tenant | No cross-tenant joins/links except prohibited; tenant-inclusive FKs required conceptually | Runtime roles scoped; verified transaction-bound tenant context required; app authorization primary | **Yes** | Licensing/identity integrity, concurrency/idempotency controls, sensitive identifiers protected (no raw ID uniqueness keys) |
| Security-internal data | Platform support approvals/governance records (if separated), security control metadata, key-rotation/control records (logical) | May be platform/security-owned or specially scoped | Strictly controlled; no tenant data leakage | Privileged security/admin paths only, audited | **Depends** (separate policies/schemas possible); tenant data remains isolated | Break-glass/audit requirements; separation of duties |
| Derived/analytics data | Materialized views/counters/projections (e.g. usage summaries), reporting aggregates | Derived from tenant-owned (or global) sources; ownership follows source scope | Tenant-derived aggregates must not cross tenant boundaries | Same or stricter than source; read-optimized roles | **Yes** when tenant-scoped | Reconciliation with authoritative records; no PII leakage in shared analytics |
| Forensic evidence data | `forensic_evidence_record`, `evidence_object_version`, `evidence_custody_event`, transition authorizations, evidence binaries/objects (external storage referenced) | Tenant-owned/contextual to tenant case unless legally governed exception explicitly defined (open) | No cross-tenant access; chain-of-custody isolation | Strong RBAC, need-to-know, audited access; controlled transitions | **Yes** where stored in DB metadata tables | Immutability/integrity/hash, legal hold/retention open decisions, separation from operational audit |

**Cross-tenant reference prevention:** Tenant-owned relationships must be modeled so physical schema can enforce tenant-inclusive foreign keys/constraints (e.g. composite references including `tenant_id`) to prevent cross-tenant references. RLS is expected defense in depth, not the only control.

## 6. Invariants and lifecycle rules (logical)

- **Licensing:** one unique monitored device = one licensed asset per tenant; data sources never billable; multiple bindings/sources/aliases for same resolved device do not create duplicate licensed usage; licensing separate from technical quotas; canonical asset IDs stable/non-reusable.
- **Identity:** `asset` distinct from `data_source`/bindings/keys/aliases/claims; raw source identifiers never used as DB uniqueness keys; fingerprints/aliases are versioned lookup identities (not permanent binding identity) and may overlap only to same stable binding; ambiguous/conflicting identity => no auto-merge, no automatic billing as confirmed device, pending/review flow per approved policy.
- **Atomicity/idempotency:** identity/licensing/lifecycle/history changes requiring consistency must be atomic and durably idempotent (ledger/outcome semantics) as designed; `event_receipt` ingestion idempotency remains distinct from `identity_operation_idempotency_ledger`.
- **Audit/evidence separation:** operational audit, forensic evidence metadata/object versions, and custody events are distinct record classes.
- **Tenant isolation:** verified transaction-bound tenant context required; no client/user-settable GUC authorization; RLS defense in depth; runtime roles not owner/SUPERUSER/BYPASSRLS.

## 9. Round 1.1 targeted consistency corrections (logical, proposed)

### 9.1 Source-device binding model (resolves/clarifies OD-002 as recommendation)

**Alternatives evaluated:**

| Alternative | Summary | Single source of truth | Cardinality | Ownership/lifecycle | Fingerprint alias references | Multiple sources reporting one canonical asset | Merge/split effects | Key rotation/alias overlap | Historical binding preservation | Referential integrity / tenant-inclusive FK feasibility |
|---|---|---|---|---|---|---|---|---|---|---|
| **A. `asset_data_source` authoritative binding entity; stable identity represented by immutable `source_device_key_id` owned by binding (Recommended, Proposed)** | Binding row is the authoritative stable source-device binding and owns `source_device_key_id`, provenance, and lifecycle; aliases reference that stable binding identity. Any separate `source_device_key` artifact is 1:1 dependent/non-authoritative only. | **Strong:** one binding authority owns stable identity and lifecycle facts. | 1 `asset_data_source` : 1 stable `source_device_key_id` : 0..* aliases; 1 asset : 0..* bindings; 1 data_source : 0..* bindings. | Clear: binding owns attach/detach/replace lifecycle and immutable stable key identity for that context. | Aliases FK/reference stable binding identity (`asset_data_source` / `source_device_key_id`) directly. | Supported naturally: many bindings (distinct source-device contexts) may resolve to same canonical asset without duplicate licensed usage. | Reassignment moves binding/alias lineage with typed operation records; survivor/losing history preserved. | Aliases versioned under same stable binding identity; overlap resolves to same binding/asset. | Binding history, lineage, and identity claims preserve provenance. | **Good:** tenant-scoped typed FKs/uniqueness feasible; no competing key table authority. |
| **B. `source_device_key` authoritative stable identity entity; `asset_data_source` references it** | Stable key row owns identity continuity; binding row is association to asset/data source referencing key. | **Risk:** binding provenance/lifecycle and key lifecycle can diverge into dual authority unless exhaustively constrained to strict 1:1 same-lifecycle ownership rules. | Potentially 1 key : 1 binding (required) or accidental 1:* misuse; must be constrained. | Split risk: ownership of "binding active/detached" vs "key active/retired" must be defined without conflict. | Aliases reference key; binding also references key/asset — integrity depends on strict coupling. | Possible if constrained, but more join/constraint complexity. | Requires coordinated updates across key/binding/alias/operation records. | Overlap feasible but anchored to separate key authority. | Possible but easier to create inconsistent historical interpretation. | Feasible only with strict 1:1 and transaction rules; higher schema/governance complexity. |

**Recommendation (Proposed, requires technical approval):** Adopt **Alternative A** as the logical default: `asset_data_source` is the authoritative stable source-device binding entity and owns immutable `source_device_key_id`; `source_device_fingerprint_alias` references this stable binding identity; a separate `source_device_key` entity is not an independent source of truth and, if materialized, must be 1:1 dependent/non-authoritative with identical lifecycle and no competing attributes. **This is a documented recommendation only and is not approved.** Precise technical approval is required for OD-002 before physical schema finalization.

### 9.2 Identity/licensing idempotency contract (proposed)

**Scope:** `identity_operation_idempotency_ledger` for identity/licensing/lifecycle operations requiring durable retry safety (e.g. registration, attachment, alias/rotation steps as designed, conflict resolution actions, merge, split, lifecycle transitions, quota/reservation operations). **Not** ingestion `event_receipt` and **not** outbox attempt/replay metadata.

**Proposed logical contract fields/semantics:**
- **Key scope:** `(tenant_id, operation_type, idempotency_key)` unique within approved retention/reconciliation scope; key supplied or derived per operation contract.
- **Operation type:** explicit enumerated/logical operation class (must match the business operation).
- **Request canonicalization:** deterministic canonical form of request identity/effect inputs (excluding non-semantic transport metadata) before hashing/comparison.
- **Request hash/fingerprint:** stored canonical request hash/digest; used to detect semantic mismatch.
- **Actor/source context (logical):** authenticated actor/service/source and correlation references as required for auditability.
- **Processing state:** proposed states `in_progress`, `committed`, `failed_terminal` (no committed business effect for that key), `timeout_unknown_commit` (outcome ambiguous, reconciliation required).
- **Committed outcome/result:** durable reference/value sufficient to return the original committed result (affected IDs/states/counters deltas or result envelope) without reapplying effects.
- **Attempt/lease metadata (if used):** claim owner/token/time bounds to prevent concurrent duplicate execution; required for staged recovery patterns.
- **Timestamps/retention markers:** created/updated/completed/expiry-or-reconciliation metadata per approved policy.

**Behavioral rules (proposed):**
- **Same key + same canonical request:** if `committed`, return original outcome; if `in_progress`, do not execute duplicate side effects (wait/conflict/serialized retry per design); if `timeout_unknown_commit`, return ambiguous state requiring reconciliation (not blind success/failure).
- **Same key + different canonical request/hash:** reject as idempotency conflict; do not execute.
- **Concurrent identical requests:** first claimant/transaction establishes `in_progress` or directly commits; others observe same-key state and follow same-request rules (no duplicate business effects).
- **Retry after successful commit:** return stored committed outcome (idempotent replay).
- **Retry after rollback/failed terminal (no commit):** only if operation is explicitly retryable and ledger semantics permit a new attempt for that key/state; otherwise preserve terminal failure semantics (policy/design-dependent, must be explicit).
- **Timeout/unknown-commit:** record `timeout_unknown_commit` when client/worker cannot prove commit or rollback; require reconciliation against durable DB state before returning definitive success; never assume commit/rollback.
- **Retention/reconciliation:** ledger records/outcomes must be retained long enough to cover retry/unknown-commit windows and audit/reconciliation needs (owner/operations approval required).

**Alternatives compared:**

| Approach | Correctness/failure implications | Advantages | Disadvantages | Recommended use |
|---|---|---|---|---|
| **A. Single-transaction coupling** (claim/ledger + business state + audit/history/licensing/counters + required outbox records committed together) | Strongest database-local atomicity: commit makes both business effect and durable replay outcome visible; rollback removes both. Unknown-commit after DB response loss is recoverable by reading committed ledger/result. Concurrent duplicates blocked by unique key/locking within transaction scope. | Simple recovery model, prevents duplicate committed effects, aligns with required "atomic and durable idempotency" invariant. | Longer transactions/contention possible; cannot include external side effects. | **Recommended default for database-local identity/licensing operations (Proposed).** |
| **B. Staged/multi-transaction tracking** (`in_progress` claim, separate business commits, finalize result) with leases/fencing and recovery | Can reduce contention or support long workflows but introduces split-brain windows (claim without final outcome, outcome without consistent claim state) unless carefully fenced; crash/timeout recovery is complex. | Flexibility for long-running or externally coordinated steps. | Higher correctness risk (duplicate apply/finalize, orphan in-progress, fence bypass) and heavier reconciliation logic. | Use only where a single DB-local transaction is not feasible and strict fencing/recovery semantics are explicitly designed and approved (not default). |

**Conclusion (Proposed):** Use **single-transaction coupling (A)** as the default for database-local identity/licensing operations; represent external/non-DB effects only via outbox/reconciliation patterns and never as exactly-once within the same commit. OD-008 remains open pending technical approval of final scope/state-machine/retention details.

### 9.3 Event receipt deduplication namespace (proposed)

**Required provenance and namespace components (logical):** `tenant_id`, `data_source_id`, `dedup_namespace_type`, `dedup_namespace_id` (or equivalent explicit derivation), normalized `source_event_key`, connector/provenance metadata, payload hash/conflict evidence as policy requires. Raw source identifiers must not be DB uniqueness keys.

**Alternatives evaluated:**

| Namespace basis | When appropriate | Collision risk across devices | Notes |
|---|---|---|---|
| Tenant + `data_source_id` | Upstream event ID is **globally unique within the connector/data-source instance** across all devices it reports. | **Low** for that connector if uniqueness guarantee holds. | Must not be used when IDs are only device-scoped for multi-device connectors. |
| Tenant + stable source-device binding identity (`asset_data_source` / `source_device_key_id`) | Upstream event ID is **unique only within a particular reported device** (common for device-local sequences). | **Prevents cross-device collisions** for same data source. | Requires known/resolvable binding context; pending/unbound identity handling must be explicit. |
| Explicitly modeled event namespace (recommended logical contract, Proposed) | All connector cases, including mixed or evolving behavior. | **Lowest when correctly populated:** namespace type/id selected from provenance and connector capability. | Stores namespace kind (e.g. `data_source_global`, `device_binding_scoped`, `connector_defined`) and resolved namespace identifier; supports validation and auditability. |

**Recommendation (Proposed):** Use an **explicitly modeled deduplication namespace** recorded on `event_receipt`: for connectors whose upstream IDs are globally unique within the data source, namespace = tenant + `data_source_id`; for connectors whose upstream IDs are device-scoped only, namespace = tenant + authoritative stable source-device binding identity (or approved pre-binding surrogate namespace with deterministic collision prevention); for unreliable/missing upstream IDs, require deterministic fallback key strategy or rejection/quarantine per approved connector policy (**Open Decision/connector-specific**). This prevents duplicate keys from different devices colliding when one connector reports multiple devices. `event_receipt` ingestion idempotency remains separate from `identity_operation_idempotency_ledger`.

### 9.4 Asset lineage relational integrity correction (proposed)

**Problem with current model:** `asset_lineage_link.from_asset_or_op_ref` is a polymorphic/generic reference to multiple entity types and **cannot be enforced by a conventional relational foreign key**. Relying on application-only validation is insufficient where structural integrity is possible.

**Alternatives evaluated:** (a) typed source/target asset references only (loses explicit operation linkage), (b) explicit operation-to-lineage entities, (c) separate merge-lineage and split-lineage associations/tables, (d) single `asset_lineage_link` table with typed nullable FKs and link-type constraints.

**Recommended correction (Proposed):** Use **typed, relationally enforceable lineage associations**. Preferred logical shape: `asset_lineage_link` records carry `tenant_id`, `link_type`/role, `from_asset_id` FK, `to_asset_id` FK, and exactly-one typed operation FK per applicable link kind (`merge_operation_id` for merge lineage, `split_operation_id` for split lineage) with mutual exclusivity/validity by `link_type` (enforceable structurally in physical design). Merge/split operation entities remain authoritative for operation facts (survivor/source/result, authorization, evidence, outcome). This preserves canonical asset identity, non-reusable asset identifiers, merge survivor/losing history, split source/result history, tenant boundaries, auditability, and referential integrity.
