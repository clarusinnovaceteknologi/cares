# CARES PostgreSQL Physical Schema Open Decisions (Round 2)

**Status:** Proposed decision register update for physical schema design; **NOT IMPLEMENTED, NOT TESTED**. This document carries forward Round 1/1.1 open decisions and records additional physical-design decisions. **No unresolved decision is marked Approved.** Existing ADR statuses remain unchanged (**ADR 0006 remains Proposed**). No approval, implementation, or production-readiness claim is made.

**Sources:** [POSTGRESQL_SCHEMA_OPEN_DECISIONS.md](./POSTGRESQL_SCHEMA_OPEN_DECISIONS.md), [POSTGRESQL_LOGICAL_MODEL_ROUND1_1_FINAL_AUDIT.md](./POSTGRESQL_LOGICAL_MODEL_ROUND1_1_FINAL_AUDIT.md), Round 2 physical design documents.

## 1. Status definitions

| Status | Meaning |
|---|---|
| **Approved** | Formally approved by required authority and documented as approved. Not used for unresolved items in this round. |
| **Proposed** | Recommended/design-documented baseline or option, pending required review/approval/validation. |
| **Deferred** | Intentionally postponed (typically to implementation planning/validation) with known dependencies and no silent assumption. |
| **Blocked** | Cannot be finalized because required external input, approval, prerequisite decision, or validation is missing. |

## 3. New physical-design decisions (Round 2)

| ID | Decision | Options considered | Recommended / proposed direction | Status | Impact | Approval/validation authority |
|---|---|---|---|---|---|---|
| PD-001 | UUID generation/version and ordering strategy for PKs and high-insert tables | UUIDv4 (random), UUIDv7/time-ordered (if supported/tooling aligned), application-generated vs DB-generated | **Proposed:** application-generated UUID with time-ordered variant preferred for insert-heavy/index-locality-sensitive tables if platform/tooling support is confirmed; otherwise UUIDv4 acceptable with measured index impact | **Proposed** | Index locality, bloat, write amplification, ID exposure characteristics | Engineering + DBA/review; workload validation (OD-012) |
| PD-002 | State/type representation: PostgreSQL enum vs constrained `text` + CHECK vs lookup tables | Native enum, text+CHECK, lookup/reference tables | **Proposed:** constrained `text` + CHECK for evolving states in initial physical design; lookup tables for governed catalogs where referential management adds value | **Proposed** | Migration flexibility, integrity clarity, governance overhead | Engineering/architecture review |
| PD-003 | Tenant-consistent referential enforcement pattern for surrogate-key relationships | Single-column FK only, composite unique `(tenant_id,id)` + composite FK, trigger-based validation, mixed | **Proposed:** composite unique keys and composite FKs for critical tenant-owned parent/child relationships where feasible; document exceptions and compensating controls | **Proposed** | Cross-tenant reference prevention, schema complexity, FK width/index cost | Security/DB design review; implementation validation |
| PD-004 | Physical materialization of `core.source_device_key` dependent projection | Materialized 1:1 table, no separate table (binding-owned columns only) | **Proposed:** prefer binding-owned authoritative columns without separate projection unless constraints/readability require table; if materialized, enforce strict 1:1 and non-authoritative parity | **Proposed** (bounded) | Schema simplicity vs explicit projection object; divergence risk if misimplemented | Architecture/security review aligned with OD-002 |
| PD-005 | Verified tenant-context database mechanism (within invariants) | Hardened security-definer helper validating protected transaction-bound context record/token; other non-GUC, non-client-authoritative mechanisms | **Proposed:** trusted transaction-bound verified-context mechanism validated by hardened helpers/internal structures; **never** client-supplied tenant IDs or user-settable GUC authorization | **Proposed** | RLS correctness, pooling safety, implementation complexity | Security/DBA/architecture approval and penetration/negative testing |
| PD-006 | RLS FORCE behavior and table ownership hardening details | Enable RLS only, enable + FORCE where applicable, role/ownership matrix specifics | **Proposed:** enable RLS on tenant-protected tables and apply FORCE where compatible with controlled ownership/bypass design; exact applicability finalized in implementation review | **Deferred** | Bypass risk, administrative operability | Security/DBA review |
| PD-007 | Outbox claim mechanism and lease/fencing implementation details | `FOR UPDATE SKIP LOCKED` claim, advisory locks, lease-token CAS updates, hybrid | **Proposed:** DB-row claim with lease token/expiry/heartbeat and atomic state transitions; `SKIP LOCKED` pattern likely suitable but must be validated | **Proposed** | Throughput, contention, duplicate processing safety (at-least-once) | Engineering validation (OD-009/OD-012) |
| PD-008 | Event receipt dedup uniqueness predicate finalization per connector/namespace | Single global unique, multiple partial uniques by namespace/id basis, generated canonical key column | **Proposed:** multiple explicit partial/conditional unique indexes matching approved namespace semantics and fallback rules | **Proposed** | Correctness of dedup, index count/write cost | Engineering/architecture approval with OD-013 |
| PD-009 | JSONB indexing policy for operational/SOC/inventory attributes | No JSONB indexes, selective expression indexes, targeted GIN indexes | **Proposed:** no default GIN indexes; add selective expression/GIN indexes only for proven query paths with sensitivity review | **Proposed** | Query flexibility vs write/storage/maintenance cost and data exposure | Engineering/DBA validation |
| PD-010 | Partitioning adoption triggers and initial partition keys | No partitioning now, immediate partitioning, threshold-based deferred adoption | **Proposed:** defer partitioning; adopt only after measured volume/query/maintenance thresholds are met, with partition-key-inclusive uniqueness design | **Deferred** | Operability, migration complexity, query/index behavior | DBA/operations with OD-010/OD-012 |
| PD-011 | Cryptographic/hash representation for evidence and fingerprint-protection artifacts | `text` encoding, `bytea`, algorithm metadata columns | **Proposed:** store algorithm identifier plus hash/derived value in consistent encoded form; exact type chosen for interoperability/indexing needs | **Proposed** | Verification tooling, storage/index behavior | Security/engineering review (OD-006/OD-010) |
| PD-012 | Physical handling of global-vs-tenant detection rules and platform-level audit rows | Strict tenant-only tables, nullable-scope tables with guarded access, separate global tables | **Proposed:** prefer explicit scope modeling (tenant-owned default) and separate global catalog tables where truly global; any nullable-scope/admin rows require restricted access paths and careful RLS/policy design | **Proposed** | Isolation clarity, administrative flexibility | Security/architecture review |
